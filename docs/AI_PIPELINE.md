## 1. المبدأ: هرم التكلفة

إرسال كل منشور إلى نموذج LLM مكلف هو الخطأ الأكثر شيوعاً وأغلاها في هذا النوع من الأنظمة. البديل: أربع مراحل، كل واحدة تُصفّي ما تستطيع وتُمرّر الباقي.

```
                    ┌──────────────────────┐
100% من المنشورات ─► │ Stage 1: Rule Filter │  تكلفة: 0
                    └──────────┬───────────┘  ~35% يُرفض هنا
                               │ 65%
                    ┌──────────▼───────────┐
                    │ Stage 2a: Embedding  │  تكلفة: ~0 (نموذج محلي)
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │ Stage 2b: Classifier │  تكلفة: ~0 (LogReg محلي)
                    └──────────┬───────────┘  ~55% يُحسم بثقة عالية
                               │ 10%
                    ┌──────────▼───────────┐
                    │ Stage 3: LLM         │  تكلفة: مرتفعة
                    └──────────┬───────────┘  المنطقة الرمادية فقط
                               │
                    ┌──────────▼───────────┐
                    │ Stage 4: Enrichment  │  تكلفة: 0 (حسابي)
                    └──────────────────────┘
```

**الهدف: ≤ 10% من المنشورات تصل Stage 3.** وهذه النسبة تُقاس فعلياً من `post_classifications.stage` وتُعرض في Developer Console — إن ارتفعت، فذلك مؤشر على أن Stage 2 يحتاج إعادة تدريب.

## 2. Stage 0 — التطبيع العربي

يسبق كل شيء. جودته تحدّد سقف جودة كل ما بعده.

```python
def normalize_arabic(text: str) -> str:
    text = strip_urls(text)
    text = strip_emoji(text)
    text = remove_diacritics(text)              # َ ُ ِ ّ ْ ً ٌ ٍ
    text = text.replace('ـ', '')                 # التطويل
    text = re.sub(r'[أإآٱ]', 'ا', text)
    text = text.replace('ة', 'ه')
    text = text.replace('ى', 'ي')
    text = text.replace('ؤ', 'و').replace('ئ', 'ي')
    text = normalize_arabic_indic_digits(text)   # ٠١٢ → 012
    text = collapse_repeated_chars(text, max=2)  # مشششكلة → مششكلة
    text = re.sub(r'\s+', ' ', text).strip()
    return text
```

**لماذا هذا حاسم:**

| الصيغة المكتوبة | بعد التطبيع |
|---|---|
| `إيجار` / `ايجار` / `أيجار` | `ايجار` |
| `مشكلة` / `مشكله` | `مشكله` |
| `التوثيــــق` | `التوثيق` |
| `ما يتوثققققق` | `ما يتوثقق` |

بدون التطبيع: القاموس يتضخّم بعشرات الصيغ لنفس الكلمة، كشف التكرار يفشل، و`gin_trgm` يعطي نتائج رديئة.

**مهم:** يُخزَّن النص الأصلي في `posts.text` والمطبَّع في `posts.text_normalized`. **لا يُعرض المطبَّع للمستخدم أبداً** — هو للمطابقة الآلية فقط. العرض دائماً من الأصل.

## 3. Stage 1 — Rule Filter (تكلفة صفر)

خمسة فحوص متسلسلة. أول رفض يوقف السلسلة ويُسجَّل السبب في `posts.filter_reason`.

| # | الفحص | مثال رفض |
|---|---|---|
| 1 | **Negative Keywords** | «شقة للإيجار» · «تأجير معدات» · «سيارة للإيجار» |
| 2 | **أنماط الإعلانات** | رقم جوال + سعر + «للتواصل» · روابط تسويق · «فرصة» + «حصري» |
| 3 | **إشارات Spam** | > 6 هاشتاقات · نص شبه فارغ · نسبة روابط عالية · تكرار مفرط |
| 4 | **اللغة** | لغة خارج القائمة المسموحة |
| 5 | **الحد الأدنى للطول** | < 15 حرفاً بعد إزالة المنشنات والروابط |

**نقطة تصميم مهمة:** المرفوض **لا يُحذف**. يُخزَّن بـ `status='filtered_out'` مع السبب. هذا يسمح بـ:
- قياس نسبة الضجيج الفعلية لكل استعلام وكل كلمة.
- اكتشاف أن قاعدة فلترة ترفض محتوى مفيداً (فحص عيّنة دورياً).
- تغذية `keywords.noise_rate` ببيانات حقيقية.

حذف المرفوض يعني فقدان القدرة على تحسين الفلترة نفسها — وهو ما يحوّل النظام إلى صندوق أسود.

**قواعد الإعلانات تُخزَّن في قاعدة البيانات لا في الكود**، قابلة للتعديل من الواجهة مع اختبار على عينة قبل التفعيل.

## 4. Stage 2 — Embedding + المصنّف الرخيص

### 4.1 نموذج الـ Embedding

**الاختيار: `BAAI/bge-m3`** (1024 بُعد) يعمل محلياً داخل `apps/ai`.

| المعيار | التقييم |
|---|---|
| دعم العربية | ممتاز — مُدرَّب متعدد اللغات فعلياً لا كإضافة |
| اللهجات | جيد على العربية العامية |
| التكلفة | صفر بعد التحميل |
| الخصوصية | **لا يغادر النص الخادم** — حاسم لبيانات خدمة العملاء |
| الأداء | ~500-1500 نص/ثانية على CPU (batch) |
| طول السياق | 8192 token — أطول من أي منشور |

**بدائل مدعومة عبر `EmbeddingProvider`:** `text-embedding-3-large` · `embed-multilingual-v3` · أي نموذج محلي آخر. التبديل = تغيير `settings.ai.providers.embedding` + migration لتغيير أبعاد `vector(N)`.

### 4.2 المصنّف الرخيص

**Logistic Regression فوق الـ embedding.** ليس شبكة عصبية — والسبب:

- يتدرّب في ثوانٍ على آلاف الأمثلة.
- يستنتج في ميكروثوانٍ.
- **يُعاد تدريبه تلقائياً كلما تراكمت 100 تصحيح جديد في `ai_feedback`** — وهذا ما يجعل حلقة التغذية الراجعة حقيقية لا شكلية.
- سلوكه قابل للتفسير والتنبؤ.

```python
# التدريب — بيانات جاهزة، المتجهات محسوبة مسبقاً
X = feedback.embeddings          # من ai_feedback.embedding
y = feedback.human_labels
model = LogisticRegression(max_iter=1000, class_weight='balanced')
model.fit(X, y)

# الاستنتاج
probs = model.predict_proba(embedding)
confidence = probs.max()

if confidence >= settings.confidence_threshold_stage2:   # 0.85
    return Classification(label=..., stage=2)
else:
    return None    # → Stage 3
```

### 4.3 مطابقة المشاكل المعروفة (بلا LLM)

هنا تظهر قيمة Phase 3 عملياً:

```sql
SELECT id, name_ar, 1 - (centroid <=> $1) AS similarity
FROM topics
WHERE level = 3 AND is_active AND centroid IS NOT NULL
ORDER BY centroid <=> $1
LIMIT 1;
```

إذا كان التشابه ≥ 0.82 → المنشور يُنسب لمشكلة معروفة **فوراً، بتكلفة صفر، بلا LLM**.

بعد تحليل الـ 300k رسالة وبناء الـ centroids، **الغالبية العظمى من المنشورات ستُطابَق بهذه الطريقة** — لأن الناس يشتكون من نفس الأشياء بصيغ مختلفة. هذا هو ما يجعل تكلفة Stage 3 تنخفض جذرياً بعد Phase 3.

### 4.4 عتبة الثقة كأداة تحكم بالتكلفة

```
عتبة 0.95 → دقة أعلى، منشورات أكثر تصل Stage 3، تكلفة أعلى
عتبة 0.75 → دقة أقل، تكلفة أقل
```

قابلة للضبط من `settings`. Developer Console يعرض التوزيع الفعلي: كم % حُسم في Stage 2؟ ما دقة Stage 2 مقابل تصحيحات البشر؟ **ضبط رقم واحد يوازن بين الدقة والتكلفة** — بلا لمس كود.

## 5. Stage 3 — LLM (المنطقة الرمادية فقط)

### 5.1 متى يُستدعى

- ثقة Stage 2 < العتبة.
- تصنيف متعارض (relevant لكن sentiment غير حاسم).
- منشور بـ `risk_score` مرتفع (يستحق تحليلاً دقيقاً بلا نظر للثقة).
- منشور من حساب مؤثر.
- عينات Query Sandbox (كلها، لأن العينة صغيرة والدقة أهم).

### 5.2 التجميع (Batching)

**لا استدعاء لكل منشور.** المنشورات تُجمَّع كل 5 دقائق وتُرسل دفعة واحدة (20-40 منشور) مع مخرج JSON منظَّم.

```
40 منشور في استدعاء واحد ≈ 1/15 تكلفة 40 استدعاء منفصل
```

السبب: التعليمات (system prompt + التصنيفات + التصنيف الشجري) تُرسل **مرة واحدة** بدل 40 مرة. مع prompt caching يصبح التوفير أكبر.

### 5.3 شكل الطلب

```json
{
  "task": "classify_posts",
  "taxonomy": { "ejar": { "العقود": ["توثيق العقد","التجديد","الفسخ"] } },
  "posts": [
    { "id": "p1", "text": "العقد ما يتوثق من أمس والدعم ما يرد" },
    { "id": "p2", "text": "شقة للإيجار في حي النرجس" }
  ],
  "output_schema": {
    "relevance": "relevant|irrelevant|advertisement|spam|unknown",
    "intent": "complaint|inquiry|suggestion|praise|news|experience|warning|issue|request|other",
    "sentiment": "very_positive|positive|neutral|negative|very_negative",
    "program": "string|null",
    "service": "string|null",
    "topic": "string|null",
    "subtopic": "string|null",
    "issue": "string|null",
    "confidence": "number 0-1",
    "reasoning_ar": "جملة واحدة"
  }
}
```

**`reasoning_ar` مطلوب لسببين:** يحسّن جودة التصنيف (تفكير قبل الإجابة)، ويُعرض للمستخدم في واجهة التصحيح ليفهم لماذا صنّف النظام هكذا — وهذا يجعل التصحيح البشري أدق.

### 5.4 محاسبة التكلفة

كل استدعاء يُسجَّل: `llm_tokens_in` · `llm_tokens_out` · `llm_cost` · `model`. تكلفة الـ AI تظهر في Cost Center **منفصلة عن تكلفة X API** — ميزانيتان مستقلتان لأن مصدرهما وسلوكهما مختلفان تماماً.

## 6. Stage 4 — الإثراء (تكلفة صفر)

### 6.1 Risk Score (0-100)

```
risk = 100 × Σ (weight_i × normalized_factor_i)
```

| العامل | الوزن | التطبيع |
|---|---|---|
| المشاعر السلبية | 0.20 | very_negative=1.0, negative=0.7, neutral=0.2 |
| متابعو الحساب | 0.15 | `log10(followers) / 7` محدود بـ 1 |
| سرعة التفاعل | 0.20 | `velocity / p95_velocity` محدود بـ 1 |
| إجمالي التفاعل | 0.10 | `log10(engagement) / 5` |
| كلمات حساسة | 0.15 | 1.0 عند وجود أي كلمة `type='sensitive'` |
| نمو مشابه | 0.15 | نمو منشورات نفس المشكلة خلال ساعتين |
| حساب مؤثر | 0.05 | 1.0 إذا `influence_score` ≥ العتبة |

**الأوزان من `settings.scoring.risk_weights`** — قابلة للضبط بلا نشر.

**`risk_factors` يُخزَّن كـ JSONB بشرح مقروء:**

```json
{ "score": 91, "factors": [
  { "name_ar": "حساب مؤثر", "contribution": 18, "detail": "142,000 متابع" },
  { "name_ar": "سرعة انتشار مرتفعة", "contribution": 20, "detail": "340 تفاعل/ساعة" },
  { "name_ar": "مشاعر سلبية جداً", "contribution": 20 },
  { "name_ar": "ارتفاع شكاوى مشابهة", "contribution": 15, "detail": "+340% خلال ساعتين" }
]}
```

**رقم بلا تفسير عديم الفائدة في نظام دعم قرار.** المستخدم يجب أن يرى *لماذا* 91 لا أن يثق بها عمياً.

### 6.2 Influence Score

**لا يعتمد على المتابعين وحدهم** — حساب بمليون متابع لا يتحدث عنا إطلاقاً ليس مؤثراً بالنسبة لنا.

| العامل | الوزن |
|---|---|
| `log10(followers)` معياري | 0.25 |
| متوسط التفاعل على منشوراته المرتبطة | 0.25 |
| عدد منشوراته المرتبطة بنا | 0.20 |
| الوصول التقديري | 0.15 |
| الاتساق التاريخي (نشاط مستمر لا لمرة واحدة) | 0.15 |

يُحسب يومياً في `score:influence`. الحسابات فوق العتبة تنتقل إلى `cache_tier='influencer'` (تحديث كل 24 ساعة).

## 7. Historical Analysis — 300,000 رسالة

### 7.1 القيد الحاكم

تحليل 300k رسالة بـ LLM لكل رسالة = **مستحيل مالياً وغير ضروري**.

**الحل: الـ Clustering يقلّل المشكلة من 300,000 إلى ~500.**

```
300,000 رسالة → embeddings (محلي، مجاني)
              → clustering (محلي، مجاني)
              → ~500 عنقود
              → 500 استدعاء LLM للتسمية
              
التوفير: 600×
```

### 7.2 خط الأنابيب الكامل

```
┌──────────────────────────────────────────────────────────────┐
│ [1] Upload & Parse                                           │
│     Excel/CSV → قراءة تدفقية (لا تحميل كامل بالذاكرة)        │
│     كشف الأعمدة تلقائياً + خريطة حقول يؤكدها المستخدم        │
```

### 7.4 المخرجات النهائية

| المخرج | الوجهة | الأثر |
|---|---|---|
| شجرة Taxonomy | `topics` (3 مستويات) | التصنيف يصبح دقيقاً وخاصاً بنا |
| كلمات مُثراة | `keywords` | استعلامات X أدق → تكلفة أقل |
| مرادفات وأخطاء إملائية | `keyword_aliases` | التقاط ما كنا نفوّته |
| **Issue Centroids** | `topics.centroid` | **مطابقة فورية بلا LLM** |
| عبارات شائعة | `keywords` (phrases) | عبارات دقيقة عالية الدقة |

**الأهم هو الـ Centroids.** بعد هذه المرحلة، منشور جديد على X يُطابَق بمشكلة معروفة عبر استعلام `pgvector` واحد بتكلفة صفر — بدل استدعاء LLM. **هذا ما يحوّل المنصة من رصد إلى ذكاء.**

### 7.5 الخصوصية

- بيانات خدمة العملاء `data_class='internal'`.
- **Embeddings محلية إجبارياً** — النص لا يغادر الخادم.
- التسمية (Stage 7) ترسل عيّنات لـ LLM: **إن كان المزود خارجياً، يجب تفعيل `ALLOW_INTERNAL_DATA_TO_EXTERNAL_AI=true` صراحة**، وإلا يُرفض الطلب.
- **الوضع الافتراضي الآمن:** مزود محلي للتسمية أيضاً. البديل: مراجعة الحوكمة أولاً.
- إزالة PII قبل أي معالجة (أرقام جوال، بريد، هويات، أسماء عند الإمكان).

### 7.6 التكلفة الإجمالية

| المرحلة | التكلفة |
|---|---|
| Embeddings (محلي) | **$0** |
| Clustering | **$0** |
| Labeling (~500 استدعاء) | **$5 - $15** (لمرة واحدة) |
| **الإجمالي** | **أقل من $20 لمرة واحدة** |

مقابل ~$3,000+ لو أُرسلت كل رسالة إلى LLM.

## 9. Emerging Topics

`detect:emerging-topics` كل 30 دقيقة:

```
1. استخراج n-grams (2-4) من منشورات آخر ساعة
2. مقارنة التكرار بآخر 7 أيام لنفس الـ n-gram
3. المرشّح إذا:
     frequency >= 15                     (ليس ضجيجاً عشوائياً)
     AND growth_pct > 200%
     AND unique_authors >= 5             ★ حاسم: ليس شخصاً واحداً يكرر
     AND ليس موجوداً في القاموس
     AND ليس كلمة وقف
4. حساب centroid من المنشورات المطابقة
5. إذا cosine مع topic موجود > 0.85 → دمج بدل إنشاء جديد
6. → emerging_terms (status='pending')
```

**شرط `unique_authors >= 5` هو ما يمنع الإنذارات الكاذبة.** بدونه، أي شخص يكرر عبارة 20 مرة يُنشئ "موضوعاً ناشئاً" وهمياً.

**المراجعة:**
```
Approve → keywords (type='related') + إشعار بتأثيره على الاستعلامات
Ignore  → status='ignored' (لن يُقترح مجدداً)
Block   → keywords (type='negative')  ← يخفض التكلفة فوراً
```

## 10. Spike Detection

### 10.1 خط الأساس الموسمي

```
لكل (scope, metric, hour_of_week):
  mean, stddev, MAD, EWMA  من آخر 8 أسابيع
```

**`hour_of_week` (0-167) لا `hour_of_day`.** الساعة 10 صباح الأحد ≠ الساعة 10 صباح الجمعة. خط أساس يتجاهل يوم الأسبوع يعطي إنذارات كاذبة كل بداية أسبوع ويفوّت ارتفاعات حقيقية في العطلة.

### 10.2 الكشف

```python
# Modified Z-score — قوي ضد القيم الشاذة (أفضل من الانحراف المعياري هنا)
z = 0.6745 * (observed - median) / MAD

is_spike = (
    z > settings.spike_z_threshold          # 3.0
    and observed >= max(5, mean * 1.5)      # ★ حد أدنى مطلق
)
```

**الحد الأدنى المطلق ضروري.** من 1 إلى 4 منشورات = نمو 300% لكنه ليس حدثاً. بدون هذا الشرط، النظام سيغرق المستخدم بإنذارات تافهة إحصائياً — وهي أسرع طريقة لجعل الناس يتجاهلون التنبيهات كلها.

### 10.3 المخرج

```
Spike: توثيق العقود
  المرصود: 38 منشور/ساعة
  الأساس:   5 منشور/ساعة
  النمو:    +660%
  z-score:  7.2
  الشدة:    critical

  مقارنات:
    الساعة السابقة: +660%
    متوسط 24 ساعة:  +540%
    متوسط 7 أيام:   +480%
    متوسط 30 يوم:   +445%
```

## 11. Incident Detection

### 11.1 المنطق

الارتفاع وحده لا يكفي. الحادث يتطلب **إشارات متعددة متقاطعة**:

```
IF spike مكتشف
   AND عنقود دلالي متماسك (cohesion > 0.7)
   AND negative_ratio > 0.6
   AND unique_authors >= 8                    ★ ليس حساباً واحداً
THEN إنشاء Potential Incident
```

### 11.2 التجميع الدلالي

```sql
-- تجميع منشورات النافذة حول مشكلة واحدة
SELECT topic_id, count(*), avg(1 - (e.embedding <=> t.centroid)) AS cohesion
FROM posts p
JOIN post_embeddings e USING (post_id)
JOIN topics t ON t.id = p.issue_id
WHERE p.posted_at > now() - interval '2 hours'
GROUP BY topic_id
HAVING count(*) >= 10 AND avg(...) > 0.7;
```

### 11.3 درجة الثقة

```
confidence = w1×spike_severity + w2×cluster_cohesion
           + w3×author_diversity + w4×sentiment_intensity
           + w5×ticket_correlation      ← Phase 4
           + w6×influencer_involvement
```

**`author_diversity` هو أهم عامل ضد الإنذارات الكاذبة.** 50 منشوراً من 3 حسابات ليست حادثاً. 30 منشوراً من 28 حساباً حادث شبه مؤكد.

## 12. Incident Memory

عند إنشاء حادث، `detect:incident-memory` يبحث في الحوادث السابقة:

```sql
SELECT id, reference, title_ar, started_at, duration_minutes,
       total_volume, root_cause, resolution,
       1 - (centroid <=> $1) AS similarity
FROM incidents
WHERE status = 'resolved' AND id <> $2 AND centroid IS NOT NULL
ORDER BY centroid <=> $1
LIMIT 5;
```

عند تشابه ≥ 0.85 يُعرض في واجهة الحادث:

```
⟳ حادث مشابه سابق

  INC-2026-0018 — «فشل توثيق العقود»
  التاريخ:      12 مايو 2026، 09:14
  المدة:        4 ساعات 12 دقيقة
  الحجم:        450 منشور
  السبب الجذري: انقطاع خدمة التحقق من الهوية لدى المزوّد
  الحل:         استعادة الخدمة + إشعار للمستخدمين
  التشابه:      0.91
```

**هذه هي «الذاكرة المؤسسية».** الفريق الجديد يستفيد من خبرة الفريق القديم آلياً — بدل أن تُفقد المعرفة مع تغيّر الأشخاص. وهي أحد أوضح الفروق بين لوحة رصد ونظام دعم قرار.

## 13. Correlation Engine (Phase 4)

```
إشارات مستقلة تُقارن زمنياً:

  [X] ارتفاع منشورات       +220%   10:30
  [T] ارتفاع تذاكر داخلية  +180%   10:45   ← من internal (مجاميع فقط)
  [N] خبر رسمي منشور               10:00
  [E] صيانة مجدولة          09:00-11:00

→ correlation: news سبق الارتفاع بـ 30 دقيقة
→ correlation: التذاكر تبعت X بـ 15 دقيقة
→ confidence: 0.88 — حادث حقيقي عالي الثقة
```

**الفكرة الجوهرية:** إشارة واحدة قد تكون ضجيجاً. إشارات متعددة مستقلة تتقاطع زمنياً = تأكيد قوي. هذا يرفع الثقة ويقلّل الإنذارات الكاذبة بشكل حاسم.

**قيد الخصوصية:** يعمل على `internal.ticket_metrics_hourly` — أرقام مجمّعة فقط، بلا أي نص تذاكر. كافٍ تماماً للارتباط، وآمن تماماً.

## 14. Executive Summary — بلا هلوسة

### 14.1 المشكلة

الملخص التنفيذي الذي يخترع أرقاماً أخطر من عدم وجود ملخص إطلاقاً. القارئ هنا متخذ قرار.

### 14.2 الحل: ثلاث طبقات

**الطبقة 1 — حقائق منظّمة فقط:**

```json
{
  "period": { "from": "2026-08-28T10:00", "to": "2026-08-28T12:00" },
  "total_relevant": 184,
  "previous_period_total": 77,
  "growth_pct": 139.0,
  "top_issue": { "name": "فشل التوثيق", "count": 132, "pct": 71.7 },
  "sentiment": { "negative_pct": 78.3, "neutral_pct": 18.5, "positive_pct": 3.2 },
  "influencers": [{ "username": "...", "followers": 142000, "posts": 3 }],
  "incidents_active": 1
}
```

**الطبقة 2 — تعليمات صارمة:**

```
اكتب ملخصاً تنفيذياً بالعربية من الحقائق المُعطاة فقط.

قواعد إلزامية:
1. لا تذكر أي رقم غير موجود في البيانات.
2. لا تستنتج أسباباً غير مذكورة.
3. لا تتنبأ بما سيحدث.
4. عند غياب معلومة، لا تملأ الفراغ — أغفلها.
5. 3-5 جمل. لغة رسمية.
```

**الطبقة 3 — التحقق الآلي بعد التوليد:**

```python
numbers_in_summary = extract_numbers(summary)
allowed = flatten_numbers(facts)

for n in numbers_in_summary:
    if not any(isclose(n, a, rel_tol=0.02) for a in allowed):
        log.error("hallucinated_number", value=n)
        return fallback_template_summary(facts)   # ★ قالب ثابت آمن
```

**إذا فشل التحقق، يُستخدم قالب ثابت بدل نص LLM.** الأمان أهم من الأناقة. تقرير بلغة قالبية صحيح أفضل من تقرير بليغ خاطئ.

كل ملخص وتوصية يُعرض بوسم واضح:

## 16. Natural Language Search (Phase 4)

### 16.1 النهج: Text-to-SQL مقيّد

**لا SQL حر من LLM.** بدلاً منه: LLM يملأ استعلاماً معلوماتياً مُقيَّداً (intent + parameters)، والنظام يبنيه.

```
"وش أكثر مشكلة تكلم عنها العملاء عن إيجار هذا الأسبوع؟"

→ { intent: "top_issues",
    program: "ejar",
    period: { from: "2026-08-21", to: "2026-08-28" },
    limit: 5 }

→ استعلام مُعدّ مسبقاً على mention_metrics_hourly
→ نتيجة مُنسّقة + مخطط
```

**النوايا المدعومة:** `top_issues` · `volume_trend` · `compare_periods` · `top_influencers` · `sentiment_breakdown` · `incident_history` · `program_summary`

### 16.2 لماذا لا SQL حر

| الخطر | الأثر |
|---|---|
| SQL injection | خرق أمني |
| استعلامات ثقيلة | تعطيل قاعدة البيانات |
| تجاوز الصلاحيات | وصول لبيانات داخلية |
| نتائج خاطئة بصمت | قرارات مبنية على أرقام غلط |

الاستعلامات المُعدّة مسبقاً: آمنة، سريعة، مفهرسة، وتحترم RBAC تلقائياً. **الحرية هنا ليست ميزة — هي مخاطرة بلا مقابل.**

## 18. AI Provider Abstraction

```python
class LLMProvider(ABC):
    name: str
    is_local: bool                      # ★ يحكم حارس الخصوصية
    @abstractmethod
    async def complete(self, prompt, *, schema=None, max_tokens, temperature) -> LLMResult
    @abstractmethod
    def estimate_cost(self, tokens_in: int, tokens_out: int) -> float

class EmbeddingProvider(ABC):
    name: str
    dimensions: int
    is_local: bool
    @abstractmethod
    async def embed(self, texts: list[str]) -> list[list[float]]
```

**التسجيل من `settings` لا من الكود:**

```json
{ "ai.providers": {
    "llm":       { "primary": "openai", "fallback": "local_qwen" },
    "embedding": { "primary": "local_bge_m3", "dimensions": 1024 }
}}
```

**حارس الخصوصية — إجباري في كل استدعاء:**

```python
if payload.data_class == "internal" and not provider.is_local:
    if not settings.ALLOW_INTERNAL_DATA_TO_EXTERNAL_AI:
        raise PrivacyViolation("internal data cannot reach external provider")
```

`data_class` **حقل إلزامي بلا قيمة افتراضية**. نسيانه يعني خطأ صريح عند التطوير — لا تسريباً صامتاً في الإنتاج. هذا فرق تصميمي مقصود.

**التبديل بين المزودين:** تعديل `settings` + إعادة حساب المتجهات إن تغيّرت الأبعاد. لا تغيير في أي منطق أعمال.
