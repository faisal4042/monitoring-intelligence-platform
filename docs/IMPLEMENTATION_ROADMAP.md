# IMPLEMENTATION ROADMAP

> خطة التنفيذ بمعايير قبول قابلة للتحقق.
> **قاعدة حاكمة:** لا يبدأ Phase تالٍ قبل استيفاء معايير القبول للحالي بالكامل.

---

## نظرة عامة

| Phase | المحور | المدة | المخرج القابل للإثبات |
|---|---|---|---|
| **0** | الأساس | 1-2 أسبوع | `docker compose up` يشغّل كل شيء |
| **1** | MVP + حماية التكلفة | 4-6 أسابيع | استعلام حقيقي يعمل بأمان تحت سقف فعّال |
| **2** | الذكاء التشغيلي | 4-6 أسابيع | تنبيه صحيح + تقرير كل ساعتين |
| **3** | العمق التحليلي | 5-7 أسابيع | Taxonomy معتمدة + حادث مكتشف آلياً |
| **4** | التكامل والقرار | 6-8 أسابيع | ارتباط مؤكد بين X والتذاكر |

**المدد تقديرية لفريق صغير (2-3 مطورين).** ما يهم هو الترتيب ومعايير القبول، لا الأسابيع.

## قواعد غير قابلة للتفاوض

هذه ليست تفضيلات — كسر أي منها يُبطل ضمانة أساسية في النظام:

1. **لا استدعاء لـ X خارج `XApiGateway`.** مفروضة بـ ESLint منذ Phase 0.
2. **لا طلب X بلا `ALLOW` من `BudgetService`.**
3. **لا استعلام في الإنتاج بلا اختبار Sandbox ناجح.**
4. **الافتراضي دائماً `LIVE_X_API=false`.**
5. **لا أسرار في Git ولا في السجلات.**
6. **لا بيانات داخلية إلى مزود خارجي بلا تفعيل صريح.**
7. **كل مخرج AI موسوم بأنه مولَّد آلياً.**
8. **كل عملية حساسة في `audit_log`.**
9. **لا حذف للمنشورات المفلترة** — هي بيانات تحسين الدقة.
10. **الأسعار والحدود والسياسات في `settings` لا في الكود.**

## الخطوة التالية المباشرة

**قبل أي كود:** حسم باقة X API الفعلية والميزانية الحقيقية.

هذا القرار يحدد:
- عدد البرامج القابلة للرصد في Phase 1 (واحد أم أربعة)
- وتيرة الاستطلاع الممكنة
- عتبة الدقة المطلوبة لجدوى التشغيل
- هل يكفي حجم البيانات لكشف spike إحصائياً

**كل شيء آخر في Phase 0 و Phase 1 يمكن بناؤه واختباره بالكامل في DEMO Mode بلا انتظار هذا القرار** — لذلك لا داعي لتعليق العمل عليه. لكن `LIVE_X_API=true` لا يجب أن يحدث قبل حسمه.
