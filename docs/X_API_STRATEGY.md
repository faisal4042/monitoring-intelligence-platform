## 1. ★ الحقيقة الأولى: X لا تبيع بالطلب

هذه النقطة تُغيّر تصميم النظام كله، ويجب استيعابها قبل أي شيء آخر.

**X تبيع اشتراكات شهرية بسقف عدد منشورات مقروءة**، لا طلبات مُسعّرة فردياً. لذلك:

```
التكلفة الحقيقية للطلب = 0
التكلفة الحقيقية = عدد المنشورات المُرجعة (posts returned)
```

**كل منشور غير مرتبط يصل إلينا هو حصة محروقة لا تُسترد.**

### 1.1 الحساب الذي يجب أن يراه صاحب القرار

بأرقام باقة Basic التقديرية (يجب التحقق منها مقابل صفحة أسعار X الحالية):

| البند | القيمة |
|---|---|
| سعر الباقة الشهري | $200 |
| سقف المنشورات المقروءة | 10,000 / شهر |
| **سعر الوحدة المشتق** | **$0.02 لكل منشور** |

**ما تعنيه ميزانية $20/شهر:**

```
$20 ÷ $0.02  =  1,000 منشور شهرياً
1,000 ÷ 30   =  ~33 منشور يومياً  ← لكل البرامج مجتمعة
```

توزيعها حسب الحصص المطلوبة:

| البرنامج | الحصة | منشور/شهر | منشور/يوم |
|---|---|---|---|
| إيجار | 40% | 400 | ~13 |
| REGA | 30% | 300 | ~10 |
| ملاك | 15% | 150 | ~5 |
| مستدام | 15% | 150 | ~5 |

**الاستنتاج التشغيلي:** عند هذا المستوى، الدقة ليست تحسيناً — هي شرط وجود. استعلام بدقة 50% يعني أن نصف الـ 13 منشور اليومي لإيجار ضجيج، فيتبقى 6 منشورات مفيدة يومياً. هذا لا يكفي لبناء أي إشارة إحصائية موثوقة (كشف spike، خط أساس، حادث).

**التوصية:** إما رفع الميزانية إلى مستوى الباقة الفعلية، أو حصر Phase 1 في **برنامج واحد** (إيجار) باستعلام واحد عالي الدقة، وتوسيع النطاق بعد إثبات نسبة الدقة عملياً.

**القرار مطلوب من صاحب المشروع قبل `LIVE_X_API=true`.** حتى ذلك الحين، النظام يعمل بالكامل في DEMO Mode بلا أي مخاطرة.

### 1.2 نموذج التكلفة في الكود

```ts
// من settings — لا رقم واحد مثبت في الكود
const pricing = await settings.get('x_api.pricing');
const unitPrice = pricing.model === 'subscription_with_quota'
  ? pricing.monthly_price_usd / pricing.monthly_post_quota
  : pricing.per_post_price_usd;      // يدعم نماذج تسعير مستقبلية

cost = postsReturned * unitPrice;
```

عند تغيّر أسعار X: يُعدَّل صفٌّ واحد في `settings`. لا نشر، لا migration، لا تعديل كود.

## 2. طبقات الدفاع السبع

```
L0  ENV Flag         LIVE_X_API=false          استحالة فيزيائية للاتصال
L1  Kill Switch      Redis flag                إيقاف فوري بكل النطاقات
L2  Budget Gate      ALLOW/DENY ذري            لا طلب بلا إذن
L3  Query Gating     Sandbox إلزامي            لا استعلام غير مختبر في الإنتاج
L4  Request Shaping  watermark + caps + fields أقل جلب ممكن لكل طلب
L5  Polling Tiers    hot/warm/cold             لا استطلاع موحّد للجميع
L6  Precision Loop   cost/relevant → توصيات    تحسين ذاتي مستمر
```

كل طبقة مستقلة. فشل واحدة لا يُسقط الباقي.

## 3. L0 — Environment Flag

```ts
if (!config.LIVE_X_API) return mockClient.handle(request);
```

أول سطر في `XApiGateway`. عند `false` **لا يوجد كود اتصال شبكي في المسار إطلاقاً** — ليس منعاً منطقياً بل عدم وجود مسار تنفيذ.

القيمة الافتراضية في `.env.example` و في `packages/config` هي `false`. التشغيل الحي يتطلب فعلاً واعياً.

**فحص الإقلاع:**
```
LIVE_X_API=true بلا X_BEARER_TOKEN        → فشل إقلاع فوري
LIVE_X_API=true بلا ميزانية مُهيّأة        → فشل إقلاع فوري
LIVE_X_API=true بلا استعلام اجتاز Sandbox → تحذير عالي + بقاء الاستعلامات موقوفة
```

## 4. L1 — Kill Switch

### 4.1 النطاقات

| النطاق | الأثر | حالة الاستخدام |
|---|---|---|
| `global` | إيقاف كل جلب من X | طارئ — استهلاك غير متوقع |
| `program` | إيقاف استعلامات برنامج | برنامج يستنزف حصته |
| `query` | إيقاف استعلام واحد | استعلام سيئ الدقة |
| `source` | إيقاف مصدر (X / news) | صيانة أو مشكلة مزود |

**المنصة تبقى تعمل بالكامل في كل الحالات.** التصنيف، التقارير، الحوادث، لوحة التحكم — كلها تعمل على البيانات المخزّنة. الإيقاف يمس **الجلب فقط**.

### 4.2 التنفيذ

```
POST /api/v1/cost/kill-switch
{ scope: "global", reason: "استهلاك غير متوقع في استعلام إيجار" }

→ 1. كتابة في Redis   (فوري — ملي ثانية)
  2. كتابة في PG      (ديمومة)
  3. audit_log        (من، متى، لماذا)
  4. SSE broadcast    (كل الجلسات المفتوحة ترى الحالة فوراً)
  5. إلغاء المهام المعلّقة في الطابور
```

**السبب حقل إجباري.** لا إيقاف مجهول السبب في السجل.

**بعد إعادة التشغيل:** `worker` يعيد بناء حالة Redis من PG عند الإقلاع. القفل لا يُفقد بإعادة تشغيل — وهذا خطأ شائع وخطير في تصاميم مشابهة.

### 4.3 في الواجهة

زر أحمر ثابت في الشريط العلوي: **`إيقاف جمع بيانات X`** — مرئي دائماً لمن يملك `killswitch:operate`، مع مؤشر حالة حي (يعمل / موقوف منذ HH:mm). لا يحتاج المستخدم للبحث عنه وقت الأزمة.

## 5. L2 — Budget Gate (القاعدة الأساسية)

> **لا يوجد أي Background Job يستطيع تنفيذ X API request بدون المرور على API Budget Service أولاً.**

### 5.1 تسلسل الفحص

| # | النطاق | الفترة | مثال حد |
|---|---|---|---|
| 1 | Emergency Stop | — | نشط/غير نشط |
| 2 | Global | month | 1,000 unit / $20 |
| 3 | Global | day | 40 unit |
| 4 | Global | hour | 10 unit |
| 5 | Program | month | إيجار: 400 unit |
| 6 | Query | day | استعلام: 15 unit |
| 7 | Purpose | day | اختبارات: 100 unit |

أول رفض يوقف السلسلة ويُسجَّل في `api_denials` بالسبب والنطاق والرقم.

### 5.2 الذرية — سكربت Lua

المشكلة: عدة workers يفحصون معاً فيرى كلٌّ منهم رصيداً كافياً، ثم يتجاوزون السقف مجتمعين (race condition كلاسيكي).

الحل: **الفحص والحجز في عملية Redis ذرية واحدة.**

```lua
-- reserve.lua
-- KEYS = عدادات كل النطاقات · ARGV = الحدود + الوحدات المطلوبة
-- يفحص كل النطاقات؛ إن نجحت جميعها يزيد الجميع ويُرجع ALLOW
-- إن فشل أي نطاق يُرجع DENY بلا أي تعديل — لا حالة وسطى
for i = 1, #KEYS do
  local used  = tonumber(redis.call('GET', KEYS[i]) or 0)
  local limit = tonumber(ARGV[i])
  if limit >= 0 and used + tonumber(ARGV[#ARGV]) > limit then
    return {0, KEYS[i], used, limit}          -- DENY
  end
end
for i = 1, #KEYS do
  redis.call('INCRBY', KEYS[i], ARGV[#ARGV])
  redis.call('EXPIREAT', KEYS[i], <period_end>)
end
return {1}                                     -- ALLOW
```

### 5.3 الحجز ثم التسوية

```
قبل الطلب:  احجز max_results (أسوأ حالة)          → 50 unit
بعد الطلب:  الفعلي = 12 منشور → أرجع 38 unit
عند الفشل:  أرجع 50 unit كاملة
```

هذا يجعل تجاوز السقف **مستحيلاً** لا مجرد غير مرجّح. الحجز المسبق أهم من المحاسبة اللاحقة.

### 5.4 عتبات التنبيه

عند 50% / 70% / 80% / 90% / 100% من أي ميزانية:

- تنبيه داخل المنصة + بريد لمن يملك `budget:write`
- `budget_counters.last_threshold_alerted` يمنع تكرار نفس العتبة
- عند **100%** مع `is_hard_limit=true`: إيقاف تلقائي لكل الجلب **غير الحرج**

**تعريف "غير الحرج":** كل شيء عدا استعلامات `polling_tier='hot'` المرتبطة بحادث نشط. حتى هذه تتوقف عند تجاوز السقف الشهري الصلب — لا استثناء يخترق الحد الأعلى.

## 6. L3 — Query Gating

```
DRAFT ──► TESTED ──► APPROVED ──► ACTIVE
  │          │            │
  │          │            └─ صلاحية query:promote + audit
  │          └─ اختبار Sandbox واحد على الأقل، precision ≥ 70%
  └─ قابل للتعديل بحرية، لا يُنفَّذ أبداً
```

`collect:query` يجلب فقط `status='active' AND NOT is_paused`. استعلام draft **غير مرئي للـ Scheduler إطلاقاً** — الحماية بنيوية لا شرطية.

### 6.1 الـ Sandbox بالتفصيل

**العينة تُخصم من الميزانية فعلياً** (`purpose='test'`). الاختبار ليس مجانياً ويجب أن يظهر في التكلفة — وإلا صار ثغرة استهلاك غير محاسَبة.

مراحل الاختبار:

1. جلب `sampleSize` منشور (10/25/50/100) — صفحة واحدة فقط، بلا pagination.
2. تمرير كامل على AI Pipeline بما فيه Stage 3 (العينة صغيرة، فالتكلفة مقبولة).
3. تصنيف: `relevant` / `irrelevant` / `advertisement` / `spam` / `unknown`.
4. `Precision = relevant ÷ (total − unknown)`.
5. **تحليل مساهمة الكلمات** — لكل كلمة في الاستعلام: كم منشوراً طابقت؟ ما نسبة الضجيج فيها؟
6. توليد توصيات محددة قابلة للتنفيذ.
7. مراجعة بشرية لكل منشور → التصحيحات تدخل `ai_feedback`.

### 6.2 شكل التوصيات

```json
{
  "recommendations": [
    { "type": "add_negative", "severity": "critical",
      "message_ar": "كلمة «تأجير» طابقت 34 منشوراً، 79% منها إعلانات معدات. يُقترح استبعادها.",
      "action": { "op": "add_negative_keyword", "term": "تأجير معدات" },
      "estimated_precision_gain": 0.21 },

    { "type": "narrow_scope", "severity": "warning",
      "message_ar": "الاستعلام يحتوي 6 حدود OR بلا مجموعة AND — اتساع مرتفع وخطر ضجيج عالٍ.",
      "action": { "op": "suggest_and_group", "terms": ["عقد","توثيق","مستأجر"] } },

    { "type": "add_keyword", "severity": "info",
      "message_ar": "ظهرت عبارة «العقد معلق» في 4 منشورات مرتبطة ولم تكن في القاموس.",
      "action": { "op": "add_keyword", "term": "العقد معلق", "type": "service" } }
  ]
}
```

**كل توصية قابلة للتطبيق بضغطة واحدة** تنشئ `query_version` جديدة. المستخدم يعيد الاختبار ويقارن الدقة بين الإصدارين. هذا هو ما يجعل §43 (Query Versioning) مفيداً فعلاً بدل كونه سجل تغييرات جامد.

### 6.3 التقدير المجاني قبل الاختبار

```
Breadth Score (0-100) = f(
   عدد حدود OR في المستوى الأعلى     ↑ يوسّع
   وجود مجموعات AND                   ↓ يضيّق
   عبارات دقيقة (phrases)             ↓ يضيّق
   عدد الكلمات السالبة                ↓ يضيّق
   عمومية الكلمة (من بياناتنا)        ↑ يوسّع
   وجود lang: / -is:retweet           ↓ يضيّق
)

Noise Risk = Breadth × (1 − negative_coverage) × avg_historical_noise(terms)
```

`avg_historical_noise` يأتي من `keywords.noise_rate` — بياناتنا الفعلية. **التقدير يتحسّن ذاتياً كلما استخدمنا النظام أكثر**، بلا أي تكلفة API.

## 7. L4 — Request Shaping

### 7.1 `since_id` — أكبر موفّر على الإطلاق

```
تشغيل 1: جلب 40 منشور → احفظ since_id = أحدث معرّف
تشغيل 2: ?since_id=<محفوظ> → 3 منشورات جديدة فقط
```

بدونه، كل استطلاع يعيد جلب نفس النافذة الزمنية ونحن ندفع مقابلها كل مرة. مع 48 استطلاعاً يومياً، الفرق بين وجوده وغيابه هو الفرق بين ~50 و~2,400 وحدة يومياً — أي **48 ضعفاً**.

**حالات خاصة:**
- انقطاع طويل → `since_id` قديم قد يعني نتائج كثيرة → `max_pages_per_run` يحدّها.
- أول تشغيل لاستعلام جديد → `start_time` بدل `since_id`، محدود بصفحة واحدة.

### 7.2 `max_results` و `max_pages_per_run`

```
max_results_per_call: 10..100   (X يسمح حتى 100)
max_pages_per_run:    1..5      (الافتراضي 1)

السقف المطلق لتشغيل واحد = max_results × max_pages
```

**`max_pages_per_run=1` هو الافتراضي المقصود.** موضوع رائج مع pagination بلا سقف = حرق حصة شهر في دقائق. لو بقيت منشورات، الاستطلاع التالي سيلتقطها — لا شيء يُفقد لأن `since_id` يتقدّم تدريجياً.

### 7.3 Field Selection

كل حقل إضافي = حجم استجابة أكبر. الحقول تُضبط من `settings.x_api.fields` لا من الكود:

```json
{
  "tweet.fields": ["id","text","created_at","author_id","lang",
                   "conversation_id","public_metrics","referenced_tweets","entities"],
  "user.fields":  ["id","username","name","description","profile_image_url",
                   "public_metrics","verified","created_at"],
  "expansions":   ["author_id"]
}
```

**`expansions=author_id` قرار مهم:** يُرجع بيانات المؤلف **ضمن نفس الاستجابة** بلا طلب `/2/users` منفصل. هذا يملأ `authors` مجاناً لغالبية الحسابات، ويقلّل الحاجة لتحديث الكاش بشكل جوهري.

**حقول مستبعدة عمداً:** `geo` (نادراً ما تُملأ)، `context_annotations` (تضخّم الاستجابة كثيراً)، `attachments` بالتفصيل (نكتفي بـ `has_media`).

### 7.4 مُرشِّحات مجانية داخل الاستعلام

تُضاف تلقائياً لكل استعلام إنتاجي (قابلة للتعطيل):

| المُرشِّح | الأثر |
|---|---|
| `lang:ar` | يستبعد لغات لا تهمنا |
| `-is:retweet` | **الأهم** — إعادات النشر تضاعف الحجم بلا معلومة جديدة |
| `-is:reply` (اختياري) | حسب الحالة؛ الردود قد تحوي شكاوى مهمة |

**`-is:retweet` وحده يخفض الحجم عادةً بـ 40-60% بلا فقدان معلومة.** هذا فلتر يُطبَّق على جانب X قبل احتساب الحصة — أي أنه توفير حقيقي لا ترشيح بعد الدفع.

## 8. L5 — Polling Tiers

| Tier | الفترة | متى | الاستهلاك اليومي التقديري |
|---|---|---|---|
| `hot` | 5 دقائق | حادث نشط · موضوع مشتعل | مرتفع |
| `warm` | 30 دقيقة | الافتراضي للاستعلامات النشطة | متوسط |
| `cold` | 6 ساعات | مواضيع منخفضة الحجم · مراقبة خلفية | منخفض |
| `manual` | عند الطلب فقط | استعلامات تحقيق | صفر |

### 8.1 الترقية والتخفيض التلقائي

```
warm → hot:   عند كشف spike أو فتح حادث مرتبط    (مؤقت، مع مؤقّت انتهاء)
warm → cold:  إذا < 5 منشورات مرتبطة خلال 24 ساعة
cold → warm:  عند ظهور نشاط جديد
any  → paused: عند precision < 40% لثلاثة تشغيلات متتالية  ★ حماية ذاتية
```

**السطر الأخير مهم:** النظام يوقف استعلاماته السيئة تلقائياً بلا انتظار تدخل بشري. استعلام يهدر المال يُعزل خلال ساعات لا أسابيع.

### 8.2 توزيع الحمل

المهام تُوزَّع بإزاحة عشوائية (jitter) داخل نافذتها لتجنّب انفجار طلبات متزامن على رأس الساعة يصطدم بحد المعدل ويُهدر محاولات.

## 9. L6 — حلقة الدقة والتحسين

### 9.1 المقاييس الأساسية

| المقياس | الصيغة | القرار المبني عليه |
|---|---|---|
| **Precision** | relevant ÷ retrieved | جودة الاستعلام |
| **Noise %** | 1 − precision | حجم الهدر |
| **Cost per Relevant Post** | التكلفة ÷ relevant | **مقياس الكفاءة الحقيقي** |
| **Cost per Detected Issue** | تكلفة الفترة ÷ حوادث مكتشفة | قيمة الرصد للجهة |
| **Wasted Units** | irrelevant × unit_price | الخسارة الصريحة بالدولار |

### 9.2 مثال Query Consumption Analytics

| Query | Retrieved | Relevant | Noise | Precision | Cost | $/Relevant | الحكم |
|---|---|---|---|---|---|---|---|
| Ejar-Contracts-v3 | 2,500 | 2,000 | 500 | 80% | $50.00 | $0.025 | ممتاز |
| Ejar-Broad-v1 | 1,000 | 100 | 900 | 10% | $20.00 | $0.200 | **إيقاف فوري** |

الصف الثاني: **$18 من أصل $20 أُنفقت على ضجيج.** بلا هذه الصفحة، الاكتشاف يأتي بعد نفاد الميزانية.

### 9.3 محرك التوصيات

`cost:optimization-scan` يومياً يفحص كل استعلام نشط:

```
IF noise% > 60% AND units > 100:
   → add_negative (مع تحديد الكلمات المسببة من keyword_contribution)

IF share_of_budget > 25% AND precision < 50%:
   → split_query أو disable_query   [critical]

IF precision < 30% لثلاثة أيام:
   → disable_query                   [critical]  ← إيقاف تلقائي متاح

IF relevant_posts == 0 خلال 7 أيام AND units > 50:
   → disable_query (استعلام ميت يستهلك بلا مقابل)

IF new_posts / retrieved < 20%:
   → reduce_polling (نستطلع أسرع من إيقاع النشر الفعلي)
```

**القاعدة الأخيرة ذكية:** إذا كان 80% مما نجلبه مكرراً، فنحن نستطلع بوتيرة أسرع من الحاجة. تخفيض الوتيرة يوفّر بلا فقدان أي منشور.

كل توصية تُخزَّن في `cost_recommendations` مع تقدير التوفير، وقابلة للتطبيق بضغطة.

## 10. User Profile Cache

### 10.1 السياسة

| Tier | فترة التحديث | من يدخلها |
|---|---|---|
| `normal` | 7 أيام | الافتراضي |
| `influencer` | 24 ساعة | influence_score ≥ العتبة أو متابعون > 50k |
| `high_priority` | 6 ساعات | مرتبط بحادث نشط · موسوم يدوياً |

كلها من `settings.author_cache.refresh_hours` — قابلة للتعديل بلا نشر.

### 10.2 الاستراتيجية الفعلية

```
1. expansions=author_id في كل بحث
   → بيانات المؤلف تصل مجاناً مع المنشور
   → upsert في authors مع تحديث profile_fetched_at

2. طلب /2/users منفصل فقط عندما:
   - الحساب لم يظهر في أي expansion (نادر)
   - تجاوز next_refresh_at وهو influencer/high_priority
   - طلب تحديث يدوي من المستخدم

3. التجميع: /2/users?ids= يقبل 100 معرّف في طلب واحد
   → author-refresh job يجمع المستحقين ويرسل دفعة واحدة
```

**النتيجة:** طلبات الملفات الشخصية تصبح نادرة جداً — غالبية البيانات تصل ضمن الاستجابة الأصلية بلا كلفة إضافية.

### 10.3 لقطات النمو

كل تحديث يكتب صفاً في `author_snapshots`. هذا يعطي: نمو المتابعين بمرور الوقت، كشف الحسابات الصاعدة، وتقدير الوصول التاريخي — كلها من بيانات نملكها أصلاً بلا طلبات إضافية.

## 11. Deduplication

### 11.1 ثلاثة مستويات

| النوع | الآلية | الإجراء |
|---|---|---|
| **Exact** | `UNIQUE (x_post_id, posted_at)` → `ON CONFLICT DO NOTHING` | تجاهل صامت |
| **Near** | SimHash (Hamming ≤ 3) على `text_normalized` | ربط بـ `duplicate_of_id` |
| **Campaign** | نفس المحتوى + عدة مؤلفين + نافذة زمنية ضيقة | **إشارة استخباراتية** |

### 11.2 تمييز الحملة

```
IF post_count >= 10 AND author_count >= 5 AND window <= 30min:
   is_campaign_suspected = true
   campaign_score = f(author_count, تركّز الوقت, تشابه النص, عمر الحسابات)
   → تنبيه: نشاط منسّق محتمل
```

**الفرق الجوهري:** شخص يكرر شكواه 5 مرات = ضجيج يُدمج ولا يُحتسب 5 مرات في المقاييس. خمسون حساباً تنشر نفس النص خلال 10 دقائق = حدث يستحق انتباهاً فورياً. الخلط بينهما يُفسد كلا التحليلين.

### 11.3 أثر التكرار على التكلفة

`api_usage.posts_duplicate` يسجّل كم مما جلبناه كان مكرراً. نسبة تكرار عالية = مؤشر مباشر على أننا نستطلع أسرع من اللازم → توصية `reduce_polling`.

## 12. Rate Limiting

```
settings.x_api.limits.search_recent_requests_per_15min: 60
```

- Token bucket في Redis لكل endpoint، مشترك بين كل الـ workers.
- عند الاقتراب من الحد: تباطؤ استباقي بدل الاصطدام.
- عند `429`: احترام `x-rate-limit-reset` + backoff أسي مع jitter.
- **`429` لا يُحتسب استهلاكاً للحصة** (لا منشورات مُرجعة) لكنه يُسجَّل في `api_usage` بـ `units_consumed=0` لأغراض التشخيص.
- تُقرأ ترويسات `x-rate-limit-remaining` من كل استجابة وتُعرض في Developer Console — رؤية حية لا تخمين.

## 13. معالجة الأخطاء

| الحالة | السلوك | إرجاع الحجز؟ |
|---|---|---|
| `401` | إيقاف الجلب + تنبيه حرج (مفتاح غير صالح) | نعم |
| `403` | تعطيل الـ endpoint في settings + تنبيه (الباقة لا تسمح) | نعم |
| `429` | backoff + إعادة جدولة | نعم |
| `5xx` | إعادة محاولة ×3 بـ backoff أسي | نعم عند الفشل النهائي |
| timeout | إعادة محاولة ×2 | نعم |
| استجابة مشوّهة | تسجيل + تخطي | لا (استُهلكت فعلاً) |

**كل الأخطاء تُسجَّل في `api_usage`** بـ `error_code` و `units_consumed=0`. Developer Console يعرض آخر نجاح، آخر فشل، ومعدل الأخطاء.

## 15. DRY RUN Mode

`X_DRY_RUN=true` مع `LIVE_X_API=true`.

كل شيء حقيقي **عدا الطلب النهائي**:

```
✅ Scheduler يعمل بجدوله الحقيقي
✅ Budget Gate يقيّم ويقرر (ويسجّل الرفض)
✅ Query Compiler يبني الاستعلام النهائي
✅ Rate Limiter يُحاكى
❌ لا HTTP، لا استهلاك، لا بيانات
```

المخرج:
```
[DRY RUN] query=Ejar-Contracts-v3 (program=ejar)
          compiled="إيجار (عقد OR توثيق) -سيارة -is:retweet lang:ar"
          since_id=1234567890
          would_consume=50 units  (~$1.00)
          budget_verdict=ALLOW  remaining_month=847 units
```

**قيمته العملية:** تشغيل النظام يوماً كاملاً بـ DRY RUN يُظهر **الاستهلاك اليومي الحقيقي المتوقع** قبل إنفاق ريال واحد. هذه هي الخطوة التي يجب أن تسبق `LIVE_X_API=true` مباشرة.

## 16. الامتثال والاحتفاظ بالبيانات

### 16.1 المبدأ

**لا نفترض أن كل البيانات يمكن الاحتفاظ بها إلى الأبد.** شروط X تحكم ما يمكن تخزينه وعرضه ولكم من الوقت، وهي عرضة للتغيير.

### 16.2 السياسات (كلها من `settings`)

| النوع | الاحتفاظ الافتراضي | الإجراء |
|---|---|---|
| استجابات API الخام | 7 أيام | حذف (`DROP PARTITION`) |
| نص المنشورات | 365 يوم (قابل للتعديل) | حذف أو إخفاء هوية |
| معرّفات المنشورات | طويل | يُحتفظ به |
| المقاييس المجمّعة | دائم | يُحتفظ به |
| ملفات الحسابات | حسب سياسة التحديث | تحديث أو حذف |
| سجل التدقيق | حسب سياسة الجهة | يُحتفظ به |

**التمييز المهم:** المجاميع الإحصائية (`mention_metrics_hourly`) ليست محتوى منشورات. الاحتفاظ بها إلى الأجل الطويل يحفظ الذاكرة التحليلية للمنصة (خطوط الأساس، ذاكرة الحوادث، الاتجاهات) حتى لو حُذف المحتوى الخام. **هذا ما يجعل الامتثال ممكناً بلا فقدان القدرة التحليلية** — نقطة تصميمية أساسية لا تفصيلاً.

### 16.3 الحذف والامتثال

`compliance:redaction-sweep` يومياً:
1. يفحص عيّنة من المنشورات المخزّنة مقابل X.
2. المحذوف/المحمي/الموقوف → `compliance_redactions`.
3. تنفيذ الإجراء المُهيّأ (حذف النص، الإبقاء على المعرّف والمجاميع).
4. تسجيل في `audit_log`.

`settings.x_api.retention.honor_deletion_requests: true` هو الافتراضي.

### 16.4 العزل المعماري

كل ما يخص X محصور في `apps/worker/src/integrations/x/`. تغيير سياسات أو أسعار أو حدود X يمس:
- صفوفاً في `settings` (لا كود)، أو
- ملفات داخل هذا المجلد فقط.

**لا شيء خارج هذا المجلد يعرف أن X موجودة.** بقية النظام يتعامل مع `Post` و `Author` مجرّدين — وهذا ما يجعل إضافة مصادر أخرى لاحقاً (§24) تغييراً إضافياً لا إعادة بناء.

## 17. قائمة التحقق قبل التشغيل الحي

قائمة إلزامية، بالترتيب:

```
[ ] 1.  تحديد باقة X الفعلية وتوثيق سعرها وسقفها في settings
[ ] 2.  ضبط الميزانية الحقيقية (شهري + يومي + ساعي)
[ ] 3.  ضبط حصص البرامج (مجموعها ≤ 100%)
[ ] 4.  استعلام واحد على الأقل اجتاز Sandbox بدقة ≥ 70%
[ ] 5.  تشغيل DRY RUN لـ 24 ساعة ومراجعة الاستهلاك المتوقع
[ ] 6.  مقارنة المتوقع بالميزانية — تعديل الوتيرة إن لزم
[ ] 7.  اختبار Kill Switch فعلياً والتأكد من عمله
[ ] 8.  تعيين مستلمي تنبيهات الميزانية واختبار وصولها
[ ] 9.  ضبط سياسات الاحتفاظ حسب سياسة الجهة وشروط X
[ ] 10. تفعيل حدود صلبة (is_hard_limit=true) على النطاق الشهري
[ ] 11. مراجعة X_BEARER_TOKEN موجود وصالح وغير مُسجَّل في أي log
[ ] 12. LIVE_X_API=true — مع مراقبة أول ساعة عن كثب
```

**البند 5 غير قابل للتخطي.** يوم واحد من DRY RUN أرخص من شهر من الاكتشاف المتأخر.
